# 模型榜单自动选源与有效数据保障实施计划

**Goal:** 用户始终优先读取最新且通过校验的可用评测数据；任一上游失败不清空榜单，服务器自动选择已支持的数据源，并保留最后有效快照。

**Architecture:** 来源适配器独立采集和校验，选源器依据真实内容与来源健康状态生成候选，发布器通过既有 v1 协议原子发布。不同基准整体切换、历史隔离；网络故障不等于已保存成绩失效。

**Tech Stack:** 现有 Python 服务、JSON 持久化、systemd、Nginx 静态发布、Swift 客户端与 XCTest。

**状态：** 2026-10-11 已按用户后续授权实施并部署；公网和已安装客户端持久快照验证通过，弹窗视觉验收未完成。本轮范围为模型评分、费用、耗时及相关历史；不扩展至账户、用量、更新或其他公共接口。不新增客户端界面和提示。

## 1. 主旨和可兑现的承诺

“最新、有效、不断档”按以下优先级执行：

1. 真实、通过校验的数据优先；禁止造数、缺失填零、用采集时间冒充判分时间。
2. 在已支持并验证的来源中选择最新可用候选；不依赖管理员日常手动切换。
3. 上游暂不可达时，继续提供最后有效数据；恢复后自动追上新成绩。
4. 不为了声称实时而用较旧在线响应覆盖较新缓存，也不拼接不同基准的排名。

边界：不能在所有上游均停更时创造新成绩；服务器全不可达且客户端首次安装、没有任何缓存时，也无法凭空提供数据。保障对象是已有有效数据不因上游故障丢失，以及在来源恢复后按调度及时更新。服务器整机故障下的新安装可用性需要独立镜像/容灾，是后续独立范围。

自动切换覆盖本轮审核后的 Radar Bench 与旧 DeepSWE 及各自有效快照，不代表自动信任任意未知接口、题库或评分规则。未知协议变化隔离后保留有效版本。

## 3. 方案选择

| 方案 | 结果 |
| --- | --- |
| 只修新接口并固定使用 | 能恢复新成绩，仍缺少持续自动降级 |

## 4. 自动选源规则

来源分为“同基准不同传输入口”和“不同评测基准”。前者校验同一语义后可替换读取入口；后者必须整体发布并切换 generation，不能比较分数高低决定优劣。

| 状态 | 自动动作 |
| --- | --- |
| 新源产生通过校验、覆盖范围合理且时间较新的完整采集批次 | 发布新源，保留旧基准独立存档 |
| 新源部分模型网络请求失败 | 保留上一份完整有效发布；本轮不发布残缺替代榜单，失败模型独立重试 |
| 新源明确返回某档尚无成绩 | 区别于请求失败；该档不填零、不借用旧基准分数；其他有效档可形成候选 |
| 新源网络失败，但其最后有效快照仍比旧源更新 | 继续提供新快照，记录降级并独立探测新旧源 |
| 当前来源无有效快照、快照校验失败，或上游明确撤销其评测有效性 | 自动选用其他已验证来源，包括旧 DeepSWE |
| 另一已审核基准确有更晚成绩且符合切换门槛 | 整体自动切换；不拼接趋势，不仅凭 HTTP 200 切换 |
| 所有在线源失败 | 继续提供最新有效持久快照；有数据时绝不发布空数组 |
| 来源恢复且取得有效新成绩 | 自动更新；健康恢复但内容相同时仅更新状态，不伪造新成绩 |
| 人工暂停或回滚 | 保留既有暂停语义，自动选源不能覆盖管理员回滚 |

具体约束：

- 同基准按每档成绩日期/日桶、内容指纹和上游修订证据判断；同日修正允许发布，禁止只靠日期去重。同基准模型时间倒退、覆盖骤降、模型消失须隔离，不能被其他模型较新日期掩盖。
- 跨基准只在固定白名单内切换。比较实际成绩日期的精度区间；日期未知或区间重叠时不声称更晚，保留当前有效来源，无当前来源时按配置优先级选择。
- 新候选覆盖应不低于该基准最近有效采集的已计分档位与题目覆盖，除非存在经验证的上游撤销/修正依据。首次新基准接入以本次完整采集建立基线，不把单一模型有分当成全榜恢复。
- 不要求每档必须完成64题：允许权威 provisional，保留 coverage/requiredTasks/scoreStatus；有效0分和无成绩 null 区分。
- 跨基准切换默认需连续两次校验成功，并至少驻留60分钟，避免频繁往返；首次接入使用部署前两次影子采集。当前快照失效且有有效备用时立即降级，不等待驻留时间。
- 保留同基准整批快照，不将不同采集批次的费用与分数凑成综合排名。本轮不引入逐模型缓存混合发布。

## 5. 数据校验与字段映射

- 新接口使用公开规定的选择参数；校验 model/effort、schema、score_version、catalog、task hash、评分策略与绑定目录。
- 保留上游150分制权威分数，不再次乘1.5；范围0–150。校验 coverage 0–64 与 score_status 的一致性。
- `api_equivalent_usd.mean` 映射费用，`elapsed_ms.mean / 1000` 映射耗时；标记 `priceAggregation=mean` 和实际 API 等效费用口径。不得沿用旧表中位数语义。
- 指标缺失或统计证据无效时，仅相应费用/耗时置空；不抹掉有效评分，不从旧基准补齐。综合榜只使用所需指标完整的模型。
- 新源每日历史仅作为UTC日期桶。无精确判分时间时 `sourceUpdatedAt=null`、`latest.date=""`，每日分数进入 `recentDays`；新增可选日桶/精度字段供服务端选源与审计使用，不伪造00:00精确判分时间。
- 最新分数与最后每日点不一致时隔离该候选，防止混合时点。费用/耗时没有同口径历史时不倒填历史、不借评分日期伪造费用历史。
- 旧表永久带历史来源属性；读取时间变新不会使旧成绩变新。源健康、成绩新鲜度、候选是否可发布分别存储。
- 成绩超过72小时无更新作为初始可配置“历史”阈值，按日桶精度保守计算；这是展示/运维状态，不是删除有效成绩或自动倒退的理由。

## 6. 调度、存储与发布

- 新源正常检查间隔建议15分钟；旧源大表正常6小时一次，需要降级时优先使用已保存快照并进行受限探测。采用5分钟轻量调度，仅入队到期来源，不增加其他公共数据的采集频率。
- 每源独立失败计数、下一次尝试、最后成功、成绩日期和错误。失败退避15/30/60分钟，故障源不能使其他源一起退避。
- 支持有上限的网络并发（初始3）、单请求25秒及整批截止时间（初始5分钟），处理429/Retry-After。确定的428、协议不匹配进入待适配状态，不密集重试。
- 采集阶段不持有全局发布锁；发布前重新读取revision及配置代次，丢弃过期候选，避免慢请求覆盖新发布或人工回滚。现有串行worker需要让其他feed在慢源期间仍可执行。
- 每个来源保留最后有效完整快照和有限历史；将内容哈希、来源响应缓存属性、逐档时间/覆盖和采集完成情况放入私有状态。仅持久化允许公开的聚合指标。
- 对外路径继续使用 `/api/codex-toolbox/v1/radar.json`。先验证并持久化规范状态，再原子导出，保持 revision/ETag 单调、重启恢复和原发布文件可读。
- 同基准更新不增加generation；不同基准自动切换使用现有 `change=activation` 与新generation，私有日志记录自动选择原因。不得引入旧客户端不识别的公开枚举。
- 发布状态以最终采用来源为准。备用源失败只影响其健康；采用有效历史数据标 historical，当前采集失败保留快照时标 upstream_error。健康取回旧历史不应标 current。
- 无内容、状态和必要检查元数据变化时避免无意义重发；读取公开接口绝不现场等待上游。
- 不新增前台说明；现有管理诊断接口输出来源健康和选源原因。管理UI结构暂不扩展。

## 8. 验收矩阵

| 场景 | 必须达到的结果 |
| --- | --- |
| 新源有效、旧源历史 | 自动发布新源；抽样评分/费用/耗时与上游一致 |
| 新源超时、旧源在线但更旧 | 保留较新有效快照，旧数据不能倒灌 |
| 当前快照确实不可用、旧源有效 | 自动降级旧源，客户端仍有可用榜单 |

| 费用坏、评分好 | 评分可用，相关费用/综合指标按缺失处理 |
| 来源恢复、出现更晚成绩 | 自动追新，无需人工启用，无重复趋势点 |
| 未知题库/评分策略变化 | 隔离候选，继续提供原有效快照 |
| 日期相同但权威内容修订 | 内容指纹识别并安全发布，不捏造新日期 |
| 跨基准切换 | generation递增，新旧历史及费用口径不混合 |
