# 卡顿与高能耗：后续客户端更新待修

记录日期：2026-10-22（Asia/Shanghai）。用户本轮要求保存发现并排查高能耗，修复安排在后续更新。状态：待实施、待真实交互与能耗验收；尚未确定版本号，未修改或发布客户端。

## 已确认的事实

1. 用户报告点击用量柱状图、用量明细和上下滚动时卡顿。10 月 17 日优化编译的独立探针对真实数据副本测得 `dailyEstimates` 两次约 2.72 / 2.71 秒；应用在 `@MainActor AppModel.recalculateTaskQuotaEstimates` 中同步调用该函数，并在每批原生额度刷新后重算。探针没有传入完整 UI 账户参数，原始转圈现场仍未捕获，因此不能说所有卡顿都已精确归因。
2. 用户 10 月 22 日截图显示 macOS 将 Codex Toolbox.app 列为“使用大量能耗”。系统多次记录 Build 63 大量写盘，10 月 17–18 日的一段记录为 34.39 GB / 75868 秒。它是累计写入统计，不表示缓存文件达到 34 GB。
3. 10 月 22 日检查仍为 1.4.1 / Build 63；账本约 55.65 MiB、原生任务快照约 23.53 MiB。现场资源计数捕获到重复整文件量级的写入。详细结果及限制见[当日核查](../verification/2026-10-22-energy-investigation.md)。

## 变更来源与审查缺口

点击柱子选日早在 1.2.0 已有。1.4.0 Build 54 增加原生任务日额度路径，Build 55 扩展旧观测估算兜底；新增日额度调用和相关算法最终归入 `f79e228`（2026-10-05），随 Build 58 正式版发布。1.4.1 / Build 63 沿用这些核心算法。`recalculateTaskQuotaEstimates` 函数本身更早已有，不能把整个函数说成此次新增。

既有 177 / 216 项测试主要验证数值、隔离与缓存语义，缺少真实历史规模的主线程时长、长期写盘和能耗门槛。用户此前同版本流畅、后续突发卡顿的变化仍需旧数据/旧版本对照；数据增长是待验证因素，不能直接定论。

## 待修任务

### PERF-01：消除主线程上的历史额度重算

- 将重计算移出主线程；合并重复刷新，过期任务取消或丢弃结果。
- 写回前校验账户、请求代次和数据版本；保持原有额度口径与账户隔离。
- 在每批数据到达时避免重算全部历史；缓存可复用结果，减少按历史窗口反复扫描。
- 验收：固定相同输入，修复前后数值一致；以当前规模及更大规模数据测试。采样柱状图选日、明细、连续滚动，确认主线程不再执行该长计算，过期结果不覆盖新日期/账户。

### PERF-02：降低后台写盘和总计算量

- 避免小量观测更新导致大账本整份编解码与写入；减少无变化写入，合并原生结果批次落盘。
- 选择增量持久化或分离热数据等方案前验证恢复与迁移；保留用户历史，不用清缓存掩盖问题。
- 固定数据、刷新设置和操作序列，比较 CPU 时间、读取/写入字节、刷新次数；应验证资源开销随新增数据量而非全历史体积增长。
- 将计算移到后台只解决响应性，不能作为能耗修复通过的依据。

### PERF-03：建立持续能耗与交互验收

- 分别覆盖收起面板、展开静置、连续交互、后台刷新、电池/接电、睡眠唤醒。
- 每种后台测试至少覆盖多个 1 分钟和 5 分钟刷新周期；记录电源、系统版本、历史规模和其他负载。
- 同一环境对比旧包与候选包 CPU、磁盘 I/O、唤醒、辅助进程及系统能耗记录；检查内存是否持续增长。
- 不以瞬时 CPU 为零、系统提示短时消失、测试/构建/公证通过代替性能验收。原始转圈须重现并验证消失；高能耗责任比例和唯一根因尚未证实。
