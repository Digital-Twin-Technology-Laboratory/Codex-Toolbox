# Codex Toolbox 1.3.1 网络恢复设计

## 背景与结论

Codex Toolbox 1.3.0 在 Mac 休眠、DarkWake、开盖唤醒和登录启动阶段，可能正好在 Wi-Fi、系统路由或本地代理尚未恢复时发起 Radar 与 Sparkle 请求。系统日志已经确认失败发生在 DNS 和 HTTP 之前，底层错误为 `NSURLErrorDomain -1009` / `No network route`；同一地址稍后可以正常返回 HTTP 200。它不是用户配置错误，也不是远端服务持续故障，而是正常网络切换暴露出的客户端恢复缺陷。

当前实现还有三个放大因素：`RefreshScheduler` 在 DarkWake 期间仍会执行；`NSWorkspace.didWakeNotification` 到达后立即刷新；Radar 与 Sparkle 都把底层英文错误直接变成持久的可见状态。1.3.1 应把这些瞬时失败视为可恢复事件，同时继续如实暴露 HTTP、数据格式、签名、解压和安装等真正需要处理的非瞬时失败。

## 方案比较

### 方案 A：两个入口分别增加延时与字符串判断

Radar 和 `AppUpdateManager` 各自匹配 `-1009`，各自延迟后重试。改动最少，但错误链展开、重试次数和中文提示会重复；Sparkle 的 `SUDownloadError` 还会把真实 `URLError` 包在 `NSUnderlyingErrorKey` 中，简单检查顶层错误会漏判。后续维护很容易再次出现两个模块语义不一致。

### 方案 B：只用 `NWPathMonitor` 阻止无网请求

集中等待 `NWPath.Status.satisfied` 后再刷新，表面上最统一。但系统路径恢复不等于 Clash Verge 的 `127.0.0.1` 代理已经能够完成 TLS；路径也可能在请求过程中再次变化。单独依赖路径监控不能替代 `URLSession` 等待、错误链分类和有限重试，还会增加一个长生命周期的全局状态源。

### 方案 C：生命周期暂停 + 原生等待 + 共用恢复策略（采用）

应用进入睡眠前停止自有刷新调度，完整唤醒后留出短暂恢复窗口，再重建调度并刷新到期数据。Radar 的 `URLSession` 开启 `waitsForConnectivity`，并只对明确的瞬时网络错误执行有限重试。Sparkle 继续完全负责 appcast、下载、Ed25519 验签、解压与安装；App 只在委托层区分手动和后台检查、展开底层错误链并决定重试或展示。这样不接管第三方更新安全链，也不会用一个全局“有网”布尔值掩盖代理和请求阶段的真实状态。

## 架构与职责

### `NetworkRecoveryPolicy`

在 `CodexToolboxCore` 新增无 UI、无 Sparkle 依赖的纯策略类型。它递归检查 `NSError` 及其 `NSUnderlyingErrorKey`，只把以下 `NSURLErrorDomain` 代码归为瞬时网络失败：未联网、连接中断、超时、无法连接主机、找不到主机、DNS 查询失败。策略同时提供固定且有上限的重试延时：前台/手动操作为 2 秒、5 秒；后台操作只额外尝试一次，延时 30 秒。

HTTP 4xx/5xx、无效 JSON、Sparkle appcast 格式、签名、解压和安装错误都不属于瞬时网络失败，不允许进入网络重试循环。策略返回分类和动作，不直接持有视图状态，保证 Radar 与更新管理器能够复用同一判断而保留各自的产品语义。

### Radar 数据链路

`URLSessionRadarClient` 负责连接级恢复：默认会话开启 `waitsForConnectivity`，每次请求仍保留现有 15 秒请求超时和 30 秒资源超时；明确瞬时失败时最多按 2 秒、5 秒再试两次，成功、取消或非瞬时失败立即结束。

`RadarRepository` 负责缓存语义：有缓存时，最终瞬时失败继续返回缓存、标记 `isStale = true`，但不生成橙色错误横幅；`StatusHeaderView` 以低干扰的“缓存”标识说明当前数据不是本轮新取。首次启动没有缓存时仍显示空状态和中文“网络暂不可用”提示，避免用户误以为 App 已损坏。HTTP、数据结构或缓存读写等非瞬时失败继续显示明确错误。任何成功请求都清除陈旧和错误状态。

### 应用睡眠生命周期

`AppDelegate` 同时观察 `NSWorkspace.willSleepNotification` 与 `didWakeNotification`。睡眠前调用 `AppModel.suspendBackgroundWork()`，停止 Radar、用量、重置卡、费率和活跃配额调度器，避免 DarkWake 中无意义地触发网络读取。唤醒时取消旧恢复任务，等待 3 秒，再调用 `resumeBackgroundWork()` 重建调度并刷新到期数据。连续通知只保留最后一个恢复任务。

3 秒不是“网络已可用”的证明，只用于避开开盖后的最早竞争窗口；后续仍由 `waitsForConnectivity` 和有限重试兜底。应用初次启动不使用固定长延迟，以免正常网络下人为拖慢数据出现，启动阶段直接依靠请求层恢复策略。

### Sparkle 更新链路

`AppUpdateManager` 保持 Sparkle 2.9.2 的 `SPUStandardUpdaterController`、appcast、自动下载、签名与安装流程不变。现有“立即检查”仍调用 `checkForUpdatesInBackground()` 以保留自定义设置页 UI，但管理器会记录这是用户发起的检查；Sparkle 自己调度的检查则标记为后台来源。每次补试还会携带原始来源和已完成次数，不把它误当作新的后台周期而重置预算。

在 `didFinishUpdateCycleFor` 中统一处理错误。若错误链包含瞬时网络失败：手动检查保持“正在重试”状态，按 2 秒、5 秒重试，耗尽后显示中文可恢复提示；后台检查只在 30 秒后补试一次，仍失败则恢复检查前的稳定状态，不留下橙色错误。非瞬时 Sparkle 错误不重试，按检查、下载、准备或安装阶段显示中文概括，同时把原始 domain/code 写入统一日志供诊断。

睡眠期若 Sparkle 正要开始新检查，委托用一个 App 内部生命周期错误拒绝该周期。这个错误是静默哨兵：完成回调中只恢复检查前状态，不进入网络重试预算，也不向用户展示错误。睡眠发生在延时补试期间时，取消补试任务并恢复检查前稳定状态。

`resetUpdateCycleAfterShortDelay()` 只用于设置变更后的 Sparkle 周期重排，不作为网络重试 API。1.3.1 不修改 Sparkle 版本，也不自行下载、解析或验证更新包。

## 用户界面语义

- Radar 有缓存且网络瞬断：继续显示榜单，在数据日期旁显示低强调“缓存”，不出现英文或橙色大横幅。
- Radar 首次启动且无缓存：显示中文网络提示和“重试”。
- 手动检查更新正在恢复：显示“网络暂不可用，正在重试检查…”，按钮保持禁用，避免并发会话。
- 手动重试耗尽：显示“暂时无法连接更新服务器，请检查网络或代理后重试。”，允许再次点击“立即检查”。
- 后台瞬时失败：不改变用户上次看到的稳定状态，不弹错误。
- appcast、签名、解压、安装等非瞬时失败：继续可见，但必须使用中文概括，原始错误仅进入日志。

## 测试与发布边界

单元测试覆盖嵌套错误链、允许重试的 URL 错误集合、重试上限、Radar 缓存降级、首次启动提示、成功后清除状态，以及手动/后台更新决策。集成测试使用现有 `URLProtocol` stub，不依赖真实断网。完整测试继续经过 SwiftPM、CoreVerification、Xcode Build/Test。

人工验收需要在本机分别覆盖：无代理/有代理启动、睡眠后开盖、手动检查更新时短暂断网、网络恢复后自动成功、非网络更新错误不循环。验收包属于 1.3.1 本地测试候选，不等于正式发布；只有用户验收通过后，才进入 Developer ID、PKG/DMG、公证、staple、Gatekeeper、Sparkle appcast 和公开 Release 流程。
