# 1.4.2 Build 64 历史迁移与回退

2026-10-23 续接验证：跨时区保留、回退再升级、导出前后中断、重复记录和事务失败重试均已通过隔离回归。候选构建与签名状态见 `v1.4.2-build64.md`；实机迁移与安装仍待用户验收。

适用范围：1.4.1 Build 63 → 1.4.2 候选。安装与真实账户验收由用户执行。本轮验证只使用隔离数据副本，没有改写正在运行的应用数据。

## 自动迁移

数据目录为 `~/Library/Application Support/CodexToolbox/`。

| 原始文件 | 新增量库 | 原始备份 |
|---|---|---|
| `usage-ledger.json` | `usage-ledger.json.sqlite` | `usage-ledger.json.pre-1.4.2-backup` |
| `native-task-quota-v1.json` | `native-task-quota-v1.json.sqlite` | `native-task-quota-v1.json.pre-1.4.2-backup` |

首次成功读取时先保留源 JSON，再按源 schema 和时区导入。线程、日桶、逐轮观测、累计值检查点、账户采样和原生快照分别保存；校验在提交前进行。每个现有存储 actor 独占自己的连接，事务中不挂起。两个存储之间没有跨库原子性要求。SQLite 使用 `journal_mode=DELETE`、`synchronous=EXTRA`、1 秒锁等待上限；没有关闭持久化同步。[SQLite 官方同步说明](https://sqlite.org/pragma.html#pragma_synchronous)

正常刷新只更新变化记录，不双写 JSON。相同百分比、不同采样时间仍是新观测；完全重复重试不写历史正文。首次迁移成本与稳态刷新分开计量。

时区变化时，有完整 rollout 可重放的线程按新时区重建日桶。缺失、归档或无法证明完整覆盖的线程保留原日期及来源时区，原始观测继续保存在库中。无法证明旧历史完整时建立保守读取检查点，保留已有汇总，后续确定追加的事件继续按来源时区计数；不能辨认的旧事件不用于重建日期。回退期间新增或修改日桶时保留逐日来源，同一日桶可能包含多个时区，标为不完整；不会把整个线程的新旧日桶强行标成同一来源。混合来源的任务不参与精确额度和费用归属，缺乏可靠归属的数据保持缺失。迁移不回填当前账户身份。

## 回退到 1.4.1

1. 退出 Codex Toolbox，备份整个数据目录。保留 SQLite、JSON 和迁移备份；不要只复制一个文件。
2. 在本源码目录执行一次兼容导出：

   ```sh
   swift run -c release ExportLegacyHistory --directory "$HOME/Library/Application Support/CodexToolbox"
   ```

   导出工具会拒绝在应用运行时改写它的活动数据目录。导出使用最新 SQLite 记录生成旧版可读 JSON，保留数据库及原始迁移备份。两个文件分别报告结果；发生错误时不应继续安装旧版，应保留目录并重试导出。
3. 导出成功后安装已保留的 1.4.1 包。不要先运行 1.4.2 再使用过时的导出文件回退。
4. 再升级时，以导出指纹识别旧版新增数据，重新验证后导入。旧版 JSON 日期格式只有秒级精度；SQLite 中保留精确时间的原始数据仍在整目录备份中。

## 失败与清除

迁移中断、损坏 JSON、锁冲突、事务失败时保留源数据；失败不能推进读取检查点、启用标志或内存数据版本。先修复磁盘/文件问题再重试，不要以删除数据库或恢复空历史处理错误。

用户主动清除历史会持久化清除状态。迁移备份不会自动参与恢复，避免已清除数据复活。历史清除后仍保留的 Codex rollout 可能按原有产品规则重新统计；这与迁移备份恢复是不同路径。

离线测试覆盖的是故障注入、锁失败和事务回滚，不等同于真实断电或耗尽系统盘测试。真实故障操作不要在唯一数据副本上执行。
